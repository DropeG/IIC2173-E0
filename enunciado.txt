Introducción al proyecto del curso
A nivel general, el proyecto del curso busca dar a los alumnos una experiencia práctica del desarrollo
de un sistema de software compuesto de diferentes componentes que interactúan de formas
complejas, su modelacion y documentación. Dicho sistema será desarrollado en grupos y la idea es
que este desarrollo sea lo más parecido a un sistema real posible. Para partir con esto, la entrega 0 es
de carácter individual y en futuras entregas se trabajará en grupo. Así, el proyecto abarca temáticas
como protocolos, integraciones, seguridad, deployment, entre otros. El proyecto deberá siempre
correr en un entorno Cloud para obtener los conocimientos prácticos del desarrollo y deployment de
software en la nube.
Enunciado
LegitBusiness, imperio corporativo a nivel global ha entrado en el negocio del movimiento de bolsas de
energía con una plataforma llamada EnergyShark. Esta plataforma sirve para manejar el ﬂujo de
energía eléctrica entre ciudades
Debido a las diferencias en generación de energía, cada una de estas ciudades genera un balance
interno de energía, positivo o negativo. La idea es que posteriormente puedan movilizar energía y
hacer diversas tareas con este balance.
Como primer avance encargado por su Product Owner (el equipo docente), se van a familiarizar con el
ecosistema básico del proyecto para posteriormente manejar todas las fuentes de energía del país
Para empezar, van a escuchar eventos básicos del exchange de la central con un observer, asi como
registrarlos para consultarlos y conﬁrmar su recepción.
El evento clave que van a registrar ahora es el de demanda de energía en su ciudad. Este registro
sencillo permite saber cuanta demanda tienen en una ciudad dada.
Estos eventos tienen el siguiente schema JSON
{
    "idpk": "UUIDv4",
    "type": "demand-set",
    "packageBody": {
        "demands": [
            {
                "city": "New New york",
                "demand": 1013.123,
                "unit": "GW"
            },
            //más ciudades
            {
                "city": "Los Santos",

"demand": 10223,
                "unit": "GW"
            }
        ],
        "validUntil": "2026-12-12T00:00:00Z",
        "metaContent":"...",
        "constraints": {}, //vacío por ahora
    }
}
Donde idpk es un identiﬁcador único para el evento (no repetible) y type es el tipo de evento, que por
ahora solo es "demand-set". Los campos que reﬁeren a tiempo se entregan como fechas ISO8601 en
UTC
En este momento, el contenido de los eventos no es importante, lo importante es que puedan
recuperarlo y guardarlo en base de datos para consulta posterior. Deben guardarlo con el timestamp
receivedAt
Sobre el sistema de eventos
Cada uno de ustedes tendrá credenciales para su observer, para que asi puedan conectarse al
exchange. Cada observer se conecta a una cola llamada observer.X.q donde X representa un número
de usuario que se les va a asignar para la tarea junto con sus credenciales. Esta información les
llegara mediante un mensaje en Canvas.
Esta cola, la cual va guardando los mensajes que llegan, recibe del exchange fulﬁllment.x el cual está
alimentado por la central de eventos. Utilizando el cliente de RabbitMQ en su aplicación podrán
consumir los mensajes de esta cola. Cada consumo sacará el elemento de la cola y podrán leerlo y
procesarlo.
El broker se encuentra actualmente ubicado en
broker.iic2173.org:5671
Y será activado el lunes 17 de agosto a las 00:00 La información de los mensajes viene en un string
JSON que deben parsear para revisar que llegue igual que el schema

Puntaje
Esta entrega consiste en dos partes, la parte mínima (que todos deben lograr) que vale 75% de la nota
ﬁnal y una parte variable que también vale 25%. Sobre la parte variable, tendrán 2 opciones para
trabajar, de las que deberán escoger 1. Cada una de las que escojan para evaluar vale 25% de la nota
ﬁnal, y realizar la segunda parte puede dar hasta 5 décimas.
Los requisitos marcados como Esencial son obligatorios para que su tarea sea revisada, esto pues o
son fundamentales para el aprendizaje, o son necesarios para las siguientes entregas del proyecto. De
no cumplir con estos, su tarea no será revisada y será caliﬁcada con nota 1.
Requisitos funcionales (10p)
Consideren que no se les pide crear una interfaz para su aplicación (sin HTML), sino que debe ser una
API que entregue la información.
RF1: (3p) Esencial
Debe poder ofrecer en una API la lista del historial de demanda de electricidad. Deben incluirse al
menos todos los campos presentes en el historial
RF2: (1p)
Debe ofrecer un endpoint para mostrar el detalle de cada registro de demanda de electricidad recibido
desde el broker. La URI debe ser: {url}/history/{:id}. Acá, el campo ID sera el generado por
ustedes, el cual debe ser mostrado en el endpoint del RF4.
RF3: (2p) Esencial
La lista de demandas de electricidad debe estar paginada por default para que muestre cada 25
registros y poder cambiar de pagina cambiando un queryParam. Es decir: {url}/history?
page=2&limit=25. Queda a criterio de ustedes si permiten traer más valores mediante otro número del
limit en queryParams.

--- Slide 5 ---
RF4: (4p) Esencial
El endpoint {url}/history debe permitir ﬁltrar las demandas por cada una de sus propiedades,
especialmente los relacionados con tiempo. Por ejemplo: {url}/history?receivedAt=2025-08-08
Nota: es importante que sea paginada pues el emisor de eventos enviará miles de paquetes durante el
desarrollo y corrección de sus proyectos, por lo que si hacen una consulta a la base de datos para que
traiga todos los eventos recibidos es probable que se caigan sus entregas.
Requisitos no funcionales (20p)
RNF1: (5p) Esencial
Debe poder conectarse al broker RabbitMQ mediante el protocolo AMQP usando un servicio que
corra de forma constante e independiente de la aplicación web en un container aparte, llamado
connector. Este servicio debe alimentar a su servicio principal mediante llamadas HTTP POST. Los
eventos recibidos deben ser persistidos con su sistema para que estos puedan ser mostrados bajo
demanda. Además, su entrega debe resistir caidas de servicio del broker. Si se pierde temporalmente
la conexión con RabbitMQ, connector no debe terminar permanentemente y debe intentar
reconectarse sin intervención manual. La indisponibilidad del broker no debe impedir que master
continúe atendiendo consultas sobre eventos previamente almacenados.
NO se corregirán entregas caídas
RNF2: (4p) Esencial
Su despliegue debe estar containerizado. Debe existir un servicio dentro de un container llamado
master capaz de recibir los datos de connector, en la misma network docker de connector
RNF3: (3p)
Debe haber un proxy inverso apuntando a su aplicación web (como Nginx o Traeﬁk). Esta instancia
debe ir conﬁgurada directamente sobre su máquina EC2, no dentro de un contenedor Docker.
RNF4: (2p)
El servidor debe tener un nombre de dominio registrado bajo un tld publico (tech, me, tk, ml, ga, com,
cl, etc)
RNF5: (2p) Esencial
El servidor debe estar corriendo en una máquina EC2 con free tier.
RNF6: (2p)
Debe haber una base de datos Postgres o Mongo externa asociada a la aplicación para guardar
eventos y consultarlos. Esto puede ser en un container dentro de la máquina EC2 o en una instancia
RDS.

Balanceo de Carga con Nginx (25%) (15p)
Para escalar el servicio de forma horizontal podemos replicar el contenedor de la aplicación web y
utilizar NGINX como balanceador de carga, así podemos crear tantos servidores como nuestro
servicio necesite. Esto es altamente necesario para aplicaciones que en ciertos momentos tendrán una
carga importante y en otros no.
RF1: (5p)
Debe replicar master en al menos 2 instancias container para que corran en paralelo.
RF2: (10p)
Cada instancia de master debe ser individualmente alcanzable desde el Nginx instalado en el host. La
estrategia utilizada para exponer dichas instancias queda a criterio del estudiante.

Roadmap sugerido
Para simpliﬁcar esta primera entrega, le sugerimos seguir los siguientes pasos:
1. Ejecute pruebas de concepto para conectarse al cliente RabbitMQ.
2. Levante un servidor web HTTP que pueda leer los eventos recibidos.
3. Ponga su servicio en un container Docker.
4. Levante una máquina en AWS EC2 y abra los puertos.
5. Instale docker en la máquina.
6. Copie su aplicacion y construya el container.
7. Conﬁgure DNS para su servicio
8. Corra su servicio y termine su conﬁguración.
Todo lo que es Nginx es mejor conﬁgurarlo directamente en la instancia EC2.
